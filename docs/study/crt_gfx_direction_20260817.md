
# A. 로드맵에 언급된 상위 그래픽/미디어 레이어(Electron 대체)의 실현 가능성

> **문서 상태:** 2026-08-17 시점의 방향성 검토 자료이다. 이후
> `libcrtgfx`의 3개 OS native window, software frame, keyboard/mouse,
> Skia CPU raster, FreeType text milestone이 완료되었다. 현재 구현 상태와
> 다음 순서는 `STATUS.md`, `TODO.md`, `docs/runtime_roadmap.md`를 따른다.

webos21/crt 프로젝트의 로드맵(docs/runtime_roadmap.md)에 명시된 상위 그래픽/미디어 레이어 구축을 통한 'Electron-class' 애플리케이션 런타임 대체 목표는 저수준 C 런타임(libc/PAL) 개발과는 차원이 다른 도전 과제입니다.
이들이 구상하는 libcrtgfx(Skia + Wayland 계열), libcrtmedia(FFmpeg 기반), libcrtjs(QuickJS/V8 기반) 아키텍처의 실현 가능성(Feasibility)을 핵심 요소별로 나누어 현실적으로 평가해 드립니다.
------------------------------
## 1. 실현 가능성이 높은 부분 (긍정적 요인)

* 검증된 컴포넌트 조합: 프로젝트가 독자적인 그래픽 엔진이나 코덱을 밑바닥부터 짜는 것이 아닙니다. 이미 크롬, 안드로이드, Flutter 등에서 뼈대로 검증된 오픈소스들(Skia, FFmpeg, QuickJS/V8)을 가져와 엮는 방식이므로 기술적 근거는 확실합니다.
* QuickJS를 통한 빠른 가벼운 런타임 확보: 로드맵에서 JavaScript 엔진으로 거대한 V8 이전에 QuickJS를 먼저 타겟팅한 것은 매우 영리한 현실적 타협입니다. QuickJS는 크기가 작고 C 언어 결합도가 높아 webos21/crt가 구축한 저수준 libc/PAL 환경 위에서 빠르게 구동 환경을 만들 수 있습니다.
* 크로스 플랫폼 빌드 파이프라인의 완성도: 이미 mbedTLS, curl 같은 복잡한 C 기반 라이브러리를 3대 OS(Linux, macOS, Windows)에서 성공적으로 컴파일해낸 역량이 있으므로, C/C++ 위주인 Skia나 FFmpeg을 이들의 sysroot 환경으로 빌드해내는 것 자체는 실현 가능성이 매우 높습니다.

------------------------------
## 2. 치명적인 난관 및 걸림돌 (부정적 요인)

* Wayland 프로토콜의 Windows/macOS 이식 난이도:
* 로드맵의 libcrtgfx는 Wayland 스타일의 컴포지터 경계(Compositor Boundary)와 Chromium의 Ozone 경로를 참고하겠다고 명시했습니다.
   * Wayland는 리눅스 환경에 고도로 최적화된 디스플레이 서버 프로토콜입니다. 이를 Windows의 DWM(Desktop Window Manager)이나 macOS의 Quartz/Quartz Compositor 위에서 호환되도록 PAL 레이어를 추상화하는 것은 OS 고유의 창 관리 체계와 이벤트 루프 메커니즘을 완전히 재작성해야 하므로 난이도가 극도로 높습니다.
* Electron이 확보한 대규모 플랫폼 추상화 API의 격차:
* Electron이 강력한 이유는 단순히 웹 페이지를 띄우기 때문이 아니라, 지난 수년간 누적된 OS 기본 기능 제어 API(알림창, 트레이 아이콘, 파일 다이얼로그, 하드웨어 가속, 접근성 등)가 완벽하게 추상화되어 있기 때문입니다.
   * webos21/crt가 렌더링(Skia)과 스크립트(JS) 엔진을 올리더라도, 개발자가 실제 데스크톱 앱을 만들 때 필요한 이 방대한 '접착제(Glue) API'들을 전부 네이티브 C 코드로 직접 구현해 주지 않으면 Electron의 대체재가 될 수 없습니다.
* 유지보수 비용의 폭발(Explosion):
* Chromium과 V8 엔진은 전 세계 수천 명의 엔지니어가 매일 보안 취약점을 패치하고 성능을 개선하는 거대한 괴물입니다.
   * 이를 포크(Fork)하거나 커스텀 런타임 형태로 묶어서 독자 노선을 걷는 순간, 업스트림(Upstream)의 최신 업데이트와 보안 패치를 동기화하는 작업에만 프로젝트 전체의 에너지가 고갈될 위험이 큽니다.

------------------------------
## 3. 실현 가능한 형태의 현실적 타협점 (예상 시나리오)
만약 이 프로젝트가 Electron 전체를 완벽히 대체하겠다는 거대한 야망 대신 현실적인 타협을 거친다면 다음과 같은 형태로 실현될 가능성이 있습니다.

* Lightweight GUI Runtime (Flutter/Sciter 방식의 대안): Chromium 전체를 에뮬레이션하는 대신, JavaScript(QuickJS)로 비즈니스 로직을 짜고 Skia로 화면을 직접 그리는 '경량형 UI UI 박스' 형태입니다. Electron보다는 훨씬 가볍고, Flutter Native처럼 작동하는 임베디드/데스크톱 겸용 UI 프레임워크 런타임으로서의 포지셔닝은 충분히 실현 가능합니다.

------------------------------
## 종합 결론: ⭐️ 2.0 / 5.0 (빌드는 가능하나, Electron 수준의 생태계 대체는 불가능에 가까움)
"해당 컴포넌트들을 엮어서 화면에 무언가를 띄우고 미디어를 재생하는 PoC(개념 증명) 수준의 런타임 제작"은 현재 webos21/crt 메인 개발자의 툴체인 통제력으로 보아 충분히 실현 가능합니다.
그러나 현실적으로 생태계 관점에서 'Electron을 대체'하는 플랫폼이 되는 것은 불가능에 가깝습니다. Electron의 무서움은 단순 웹 렌더링이 아니라 수백 개의 OS 파편화를 완벽하게 숨겨주는 성숙한 API 생태계와 웹 표준 호환성에 있기 때문입니다.
따라서 이 로드맵은 'Electron의 완벽한 드롭인(Drop-in) 대체'보다는 "웹 기술(JS)과 크로스 플랫폼 C 라이브러리를 결합한 임베디드 타겟의 초경량 UI 구동 환경 개발"로 이해하는 것이 훨씬 현실적입니다.

# B. Skia와 Wayland를 윈도우/맥에 올릴 때 발생하는 기술적 충돌의 구체적 배경

제시해주신 두 가지 주제는 webos21/crt 프로젝트가 직면한 가장 거대한 기술적 장벽이자, 동시에 이 프로젝트가 존재해야 하는 가장 강력한 명분을 대변합니다. 각 주제에 대한 구체적인 배경과 깊이 있는 분석을 전달해 드립니다.
------------------------------
## 1) Skia와 Wayland를 윈도우/맥에 올릴 때 발생하는 기술적 충돌의 구체적 배경
프로젝트가 구상하는 libcrtgfx는 Wayland 스타일의 컴포지터(Compositor) 구조를 기반으로 화면을 쪼개고, Skia를 통해 컨텐츠를 렌더링하여 최종적으로 OS 화면에 출력하는 아키텍처를 지향합니다. 이것이 리눅스가 아닌 Windows와 macOS에서 작동할 때 다음과 같은 근본적인 기술적 충돌이 발생합니다.
## ① 디스플레이 서버 프로토콜 체계의 근본적 불일치

* 리눅스와 Wayland: Wayland는 클라이언트(애플리케이션)가 공유 메모리나 그래픽 버퍼(DMABUF 등)에 화면을 그려놓으면, 서버(컴포지터)가 이를 받아서 전체 화면에 합성(Composition)하는 구조입니다. 즉, 버퍼 중심의 프로토콜입니다.
* Windows (DWM) 및 macOS (Quartz): 두 운영체제는 자신만의 폐쇄적이고 강력한 창 관리 및 합성 엔진(Windows의 Desktop Window Manager, macOS의 Core Animation/Quartz Compositor)을 커널 및 OS 밀접 레이어에서 구동합니다.
* 충돌 배경: 외부 오픈소스 프로토콜인 Wayland의 그래픽 이벤트 요청(창 크기 변경, 포커스 전환 등)을 Windows의 HWND 체계나 macOS의 NSWindow 체계로 변환해주는 '브릿지 레이어'를 끊임없이 거쳐야 합니다. 이 과정에서 불필요한 메모리 복사(오버헤드)가 발생하거나 OS 고유의 윈도우 제어 최적화 기능을 상실하기 쉽습니다.

## ② 입력 시스템(Input System) 및 이벤트 루프 통합의 어려움

* 데스크톱 앱은 마우스 클릭, 키보드 입력, 터치, 창 최소화/최대화 같은 이벤트를 OS로부터 실시간으로 받아 처리해야 합니다.
* Wayland는 자체적인 입력 이벤트 프로토콜(wl_pointer, wl_keyboard)을 사용합니다. 이를 Windows의 Message Loop (GetMessage/WndProc)나 macOS의 RunLoop (NSEvent)와 동기화하는 것은 매우 까다롭습니다. 두 개 이상의 서로 다른 이벤트 루프가 충돌 없이 네이티브 스레드 상에서 조화를 이루게 하려면 극도로 정교한 비동기 바인딩 처리가 필요하며, 타이밍 이슈로 인한 입력 지연이나 데드락(Deadlock) 위험이 상존합니다.

## ③ 그래픽 가속(Backend API) 파편화

* Skia는 화면을 그릴 때 하드웨어 가속을 위해 로우레벨 그래픽 API를 사용합니다.
* 리눅스는 주로 Vulkan이나 OpenGL을 사용하므로 Wayland-Skia 조합이 자연스럽습니다. 하지만 Windows는 Direct3D (DX11/DX12), macOS는 Metal이 표준입니다.
* webos21/crt가 Windows/macOS에서 성능을 내려면 Skia가 각 OS의 네이티브 그래픽 API(Direct3D/Metal)를 바라보도록 설정한 뒤, 이 가속된 버퍼를 다시 Wayland 스타일의 추상화 레이어로 감싸안아야 합니다. 추상화 층위가 한 단계 더 늘어나면서 하드웨어 가속의 이점이 희석될 수 있습니다.

------------------------------
## 2) 임베디드 기기(스마트 TV, IoT 디바이스, 전장 디스플레이) 환경에서의 활용 가치
앞서 데스크톱(Electron 대체) 관점에서는 이 프로젝트의 실현 가능성을 낮게 평가했지만, 임베디드 기기 환경으로 눈을 돌리면 이 프로젝트의 가치는 폭발적으로 상승합니다. 프로젝트 이름에 포함된 webos라는 키워드가 암시하듯, 이 기술은 태생적으로 임베디드 환경에 최적화된 잠재력을 지니고 있습니다.
## ① 극단적인 경량화와 자원 최적화 (RAM/Storage 절감)

* Electron의 고질적 문제: Electron은 사소한 앱 하나를 띄우려 해도 수백 MB의 RAM을 먹고 파일 크기도 최소 100~200MB를 상회합니다. 자원이 극도로 제한된 저가형 IoT 기기나 스마트 TV 셋톱박스에서는 Electron 기반 앱을 구동하는 것이 불가능에 가깝습니다.
* CRT의 가치: webos21/crt는 무거운 Chromium 브라우저 전체를 올리는 대신 Android Bionic libc + QuickJS + Skia라는 초경량 조합을 지향합니다. 이를 통해 웹 기술(JavaScript)의 생산성을 유지하면서도, 시스템 메모리를 불과 수십 MB 내외로 점유하는 가벼운 그래픽 구동 환경을 만들 수 있습니다.

## ② 안드로이드 생태계 자산의 리눅스/임베디드 역이식

* 현재 수많은 임베디드 및 모바일 개발자가 안드로이드 플랫폼(Bionic libc 기반)에 맞춰 앱과 오픈소스 라이브러리를 최적화해 두었습니다.
* 일반적인 리눅스(glibc 기반)나 RTOS(실시간 운영체제) 환경에 이 코드들을 이식하려면 libc의 아키텍처 차이 때문에 수많은 컴파일 에러와 런타임 버그를 겪게 됩니다.
* webos21/crt가 Bionic 호환 레이어를 완벽히 제공해 준다면, 안드로이드용으로 검증된 수많은 네이티브 C/C++ 라이브러리(멀티미디어 코덱, 보안 모듈, 통신 프로토콜 등)를 임베디드 리눅스나 타 가벼운 OS 환경으로 고스란히 가져와 재빌드하여 사용할 수 있습니다. 임베디드 제품의 타임투마켓(Time-to-Market)을 극적으로 단축시킵니다.

## ③ 플랫폼 벤더 종속성(Lock-in) 탈피 및 레거시 장비 수명 연장

* 스마트 TV나 차량용 인포테인먼트(IVI) 시스템 제조사는 하드웨어 칩셋(AP) 바꿈질이나 OS 업그레이드 때마다 미디어 플레이어(FFmpeg 기반)나 그래픽 레이어를 매번 새로 튜닝해야 하는 고통을 겪습니다.
* webos21/crt가 하부 OS의 차이점을 완전히 격리해주는 PAL(Platform Adaptation Layer) 역할을 충실히 해준다면, 제조사는 OS나 칩셋이 바뀌더라도 동일한 GUI 어플리케이션 소스 코드를 그대로 유지할 수 있습니다. 결과적으로 소프트웨어 유지보수 비용이 혁신적으로 절감됩니다.

------------------------------
## 결론 및 요약
webos21/crt가 꿈꾸는 상위 레이어 로드맵은 일반 데스크톱 환경(Windows/macOS)에서는 OS 고유의 벽(DWM, Quartz, Metal 등)과 Electron이 다져놓은 거대한 API 생태계 때문에 험난한 가시밭길이 될 것입니다.
하지만 임베디드/IoT/스마트 가전 시장으로 타겟을 좁힌다면, "안드로이드 급의 이식성을 제공하면서도 런타임은 극도로 가벼운 자원 친화적 그래픽/미디어 엔진"으로서 독보적인 가치를 발휘할 수 있는 훌륭한 시도로 평가할 수 있습니다.

------------------------------

# C. Skia와 Wayland 부분에서 wayland를 windows나 macos에서 최적화할 방법이나 타 프로젝트 사례

Wayland 프로토콜을 Linux가 아닌 Windows나 macOS 네이티브 환경 위에서 구동하고 최적화하려는 시도는 실제로 오픈소스 진영에서 활발히 연구되고 있는 주제입니다. [1] 
이들이 기술적 한계를 극복하기 위해 사용하는 최적화 기법과 이를 증명하고 있는 타 프로젝트 사례를 정리해 드립니다.
------------------------------
## 1. 기술적 충돌을 극복하기 위한 주요 최적화 기법
Wayland를 타 OS에 올릴 때 발생하는 병목을 줄이기 위해 최신 프로젝트들은 다음과 같은 정교한 아키텍처적 트릭을 사용합니다.

* 1:1 윈도우 매핑 (Top-level to Native Window):
* 화면 전체를 하나의 가상 창으로 띄우고 그 안에서 Linux 앱들을 가두어 그리는 방식(Nested)은 느리고 이질감이 심합니다.
   * 최적화된 방식은 Wayland의 최상위 표면(xdg_toplevel)이 생성될 때마다 Windows의 HWND나 macOS의 NSWindow를 1:1로 동적 생성하여 매핑하는 것입니다. 이렇게 하면 창의 크기 조절, 최소화, 애니메이션 등을 OS 네이티브 compositor(DWM/Quartz)가 직접 제어하므로 버퍼 복사 오버헤드가 극적으로 줄어듭니다. [2, 3] 
* 제로 카피 공유 메모리 및 GPU 포워딩 (Shared Memory & DMA):
* Wayland 클라이언트가 그린 그래픽 버퍼를 타 OS의 창으로 복사할 때 cpu 연산을 거치면 최악의 병목이 생깁니다.
   * 이를 해결하기 위해 메모리 매핑(mmap) 또는 공유 메모리 파일 디스크립터(wl_shm)를 활용해, 클라이언트가 메모리에 쓰자마자 OS 네이티브 그래픽 파이프라인이 그 주소를 직접 참조하여 화면에 뿌리도록(Zero-copy 혹은 가깝게) 설계합니다. [3, 4] 
* Metal / Direct3D 벡엔드 직결 렌더링:
* Skia가 중간 가상 레이어를 거치지 않고, macOS에서는 Metal API, Windows에서는 Direct3D 레벨에서 가속된 텍스처 버퍼를 직접 생성하도록 유도합니다. Wayland 컴포지터는 단지 이 버퍼들의 메타데이터(크기, 위치, 투명도 등) 프로토콜만 주고받는 '중계인' 역할만 수행하게 하여 렌더링 효율을 극대화합니다. [3] 

------------------------------
## 2. 타 OS 기반의 Wayland 컴포지터 구현 사례
실제로 Windows와 macOS 환경에서 리눅스/Wayland 애플리케이션을 네이티브급 성능으로 구동하기 위해 등장한 혁신적인 프로젝트들이 있습니다.
## ① macOS 진영의 사례

* Wawona (와워나):
* macOS, iOS, Android를 모두 타겟으로 하는 매우 야심 찬 네이티브 Wayland 컴포지터 프로젝트입니다.
   * 리눅스 그래픽 앱의 버퍼를 Apple 기기의 네이티브 윈도우에 직접 드로잉(Direct Draw)해 주며, 네트워크 포워딩 도구인 Waypipe와 결합하여 원격 리눅스 앱을 맥 화면에 로컬 앱처럼 레이턴시 없이 띄우는 최적화를 달성했습니다. [5] 
* Cocoa-Way / Wayoa:
* Rust 및 Objective-C 기반으로 작성된 macOS 전용 Wayland 컴포지터입니다.
   * Apple의 Metal API를 통한 GPU 가속 표면 합성을 구현하여, 가상머신(VM) 없이 소켓 통신만으로 Wayland 프로토콜을 macOS 데스크톱과 자연스럽게 통합합니다. Retina 디스플레이의 HiDPI 스케일링을 완벽히 호환하도록 튜닝되어 오버헤드를 줄였습니다. [3, 6] 

## ② Windows 진영의 사례

* Microsoft WSLg (Windows Subsystem for Linux GUI):
* 윈도우 환경에서 가장 성공적이고 고도화된 Wayland 최적화 사례입니다.
   * 내부적으로 리눅스 표준 컴포지터인 Weston을 구동하되, 마이크로소프트가 개발한 RDP(Remote Desktop Protocol) 레일 기술과 VA-API 기반 하드웨어 가속 vGPU 드라이버를 윈도우 DWM과 엮었습니다.
   * 클라이언트 버퍼를 윈도우 호스트 시스템 메모리로 직접 복사하여, 윈도우 바탕화면 위에 리눅스 GUI 앱이 개별 창 형태로 마치 윈도우 프로그램처럼 부드럽고 완벽하게 통합 구동되는 압도적인 최적화를 보여줍니다.

------------------------------
## 3. webos21/crt에 주는 시사점
위 프로젝트들의 사례를 볼 때, webos21/crt가 로드맵을 현실화하기 위해 취해야 할 최적화 경로가 명확해집니다.

   1. 자체 컴포지터를 밑바닥부터 짜지 말 것: webos21/crt 팀이 Wayland 프로토콜 파서와 합성 엔진을 무리하게 독자 개발하기보다는, 이미 검증된 오픈소스 Wayland 라이브러리(wlroots 등)나 앞서 언급된 Wawona/Wayoa 같은 선행 오픈소스의 OS 바인딩 구조를 벤치마킹해야 승산이 있습니다. [7] 
   2. Skia의 타겟을 고도화할 것: Wayland 프로토콜 추상화 레이어를 얇게 유지하고, Skia가 Windows/macOS 각각의 핵심 API(Direct3D 12, Metal)로 직접 렌더링 파이프라인을 뚫어 버퍼를 생성하게 만든 뒤 이를 네이티브 OS 윈도우 핸들(HWND, NSWindow)에 바로 꼽아주는 '1:1 직결 아키텍처'를 채택해야만 실용적인 성능(60fps 이상)을 확보할 수 있을 것입니다. [3]

# D. 굳이 wayland를 꼭 써야 하는가?

질문하신 대로 "데스크톱 크로스 플랫폼 애플리케이션 런타임을 만드는데 왜 하필 윈도우나 맥에 친숙하지도 않은 Wayland 프로토콜을 우겨넣으려 하는가?"라는 의문은 이 로드맵을 바라볼 때 가장 핵심적이고 타당한 지적입니다.
결론부터 말씀드리면, webos21/crt 프로젝트 입장에서 Wayland는 '선택'이 아니라, 자신들의 핵심 철학(Android Bionic 기반 크로스 플랫폼)을 지키기 위한 아키텍처적 궁여지책(궁극의 우회로)에 가깝습니다.
왜 굳이 Wayland를 쓸 수밖에 없는지, 그리고 이를 썼을 때와 안 썼을 때의 득실을 다각도로 분석해 드립니다.
------------------------------
## 1. 굳이 Wayland를 고집하는 기술적 배경 (Why Wayland?)## ① 안드로이드 소스 이식성(Bionic 호환성)의 극대화

* 핵심 원인: 이 프로젝트의 본질은 "Android Bionic libc 기반의 소스 코드를 다른 OS에서 그대로 재빌드하는 것"입니다.
* 안드로이드의 최신 GUI 시스템은 내부적으로 SurfaceFlinger를 사용하며, Chromium의 OS 추상화 레이어인 Ozone은 안드로이드나 임베디드 리눅스를 타겟으로 할 때 Wayland 프로토콜을 가장 표준적이고 안정적으로 지원합니다.
* 만약 Wayland를 배제하고 Windows 전용 GDI/Direct3D 호출 코드나 macOS 전용 Cocoa/Metal 코드를 직접 이식하려 한다면, 프로젝트는 C 런타임(libc) 단을 넘어 각 OS의 수천 개에 달하는 고유 GUI 프레임워크 API까지 전부 구현해야 하는 모순에 빠지게 됩니다.

## ② Chromium Ozone 패스(Path)와의 유기적 결합

* 로드맵을 보면 Chromium의 Ozone 아키텍처를 참고하겠다고 명시되어 있습니다.
* Chromium Ozone은 브라우저 엔진이 하부 디스플레이 서버(X11, Wayland, Windows DWM 등)와 통신하는 레이어를 추상화해 둔 곳입니다. 이 중 리눅스/안드로이드 하부에서 가장 활발히 유지보수되는 인터페이스가 바로 Wayland 패스입니다.
* 따라서 Wayland 규격을 프론트엔드로 잡아두면, Chromium 소스 코드를 거의 수정하지 않고도 webos21/crt가 제공하는 sysroot 환경 위에서 컴파일해낼 수 있는 '지름길'이 열립니다.

## ③ 창 관리(Window Management) 및 합성 책임을 내부로 일임

* OS마다 창(Window)을 만들고, 닫고, 크기를 조절하고, 여러 창의 레이어를 겹쳐서 합성(Composition)하는 방식이 전부 다릅니다.
* Wayland 프로토콜을 중심에 두면, 애플리케이션 내부(예: 자바스크립트나 렌더러)에서 발생하는 모든 창 관리 이벤트를 Wayland 프로토콜 규격 하나로 통일하여 처리할 수 있습니다.
* 3대 OS를 다 맞추는 대신 Wayland ↔ 네이티브 OS 윈도우를 연결하는 단 한 개의 얇은 어댑터만 플랫폼별로 만들면 되기 때문에, 전체 아키텍처의 복잡도를 낮추는 효과가 있습니다.

------------------------------
## 2. Wayland 채택의 장단점 (Trade-Off 분석)

| 분석 항목 | Wayland를 사용할 때 (현재 로드맵) | Wayland를 배제할 때 (대안 아키텍처) |
|---|---|---|
| 장점 (Pros) | - 안드로이드/리눅스 오픈소스 GUI 코드 재활용 극대화 - 내부 창 관리 아키텍처의 단일 규격화 - 임베디드 리눅스 환경으로의 즉각적인 이식성 확보 | - 불필요한 프로토콜 파싱/중계 오버헤드 제거 - Windows/macOS 네이티브 성능 및 반응속도 극대화 - OS 고유의 UX(애니메이션, 접근성) 자연스러운 통합 |
| 단점 (Cons) | - Windows/macOS 단에서의 정교한 최적화 난이도 폭발 - 입력 이벤트 루프 동기화 버그 가능성 고조 - 데스크톱 환경에서 다소 이질적인 UI/UX 유발 | - 각 OS 플랫폼별(Win32, Cocoa) GUI 바인딩 코드를 밑바닥부터 파편화되게 직접 새로 다 짜야 함 (개발 리소스 고갈 위험) |

------------------------------
## 3. 대안은 없는가? (Wayland 없이 가는 길)
만약 이 프로젝트가 Wayland를 과감히 버린다면 선택할 수 있는 현실적인 대안 아키텍처는 다음과 같습니다.

* 대안 1: SDL2 / GLFW 같은 크로스 플랫폼 윈도우 프레임워크 활용
* 게임 엔진이나 멀티미디어 앱에서 흔히 쓰는 SDL2나 GLFW는 이미 Windows, macOS, Linux에서 창을 띄우고 입력 이벤트를 받는 추상화가 완벽하게 끝난 C 라이브러리입니다.
   * Wayland라는 거대한 프로토콜을 올리는 대신, Skia + SDL2/GLFW 조합을 채택한다면 저수준 윈도우 생성 및 이벤트 루프 충돌 문제를 단번에 해결할 수 있습니다. 실제로 많은 경량 GUI 엔진(예: 데스크톱 버전의 구형 Flutter embedding 등)이 이 방식을 애용합니다.
* 대안 2: WebGPU / Vulkan 표준 백엔드로 직결
* 창 관리 프로토콜(Wayland)에 집착하는 대신, 크로스 플랫폼 그래픽 표준인 Vulkan이나 차세대 웹 표준인 WebGPU 레이어를 PAL 단에 심고, 상위 UI 레이어는 이 그래픽 컨텍스트 위에서 직접 그리도록 강제하는 방식입니다. 창 관리는 최소화하고 화면 전체를 하나의 캔버스로 쓰는 방식에 유리합니다.

------------------------------
## 4. 종합 평가: Wayland 선택은 이 프로젝트의 '숙명'
질문하신 "굳이 써야 하는가?"에 대한 아키텍처적 답변은 "안드로이드 Bionic libc 소스 이식이라는 최초의 프로젝트 정체성을 유지하면서, Chromium 수준의 거대 GUI 엔진을 가장 적은 코드 수정으로 엮어내기 위한 필연적인 선택"입니다.
비록 Windows와 macOS에서 최적화 지옥을 겪을지언정, "오픈소스가 이미 만들어 둔 리눅스/안드로이드용 Wayland 그래픽 패스를 그대로 날로 먹겠다(Leverage)"는 전략인 것입니다. 만약 이들이 Wayland를 포기한다면, 그것은 프로젝트의 하부 런타임(Bionic) 설계 사상 자체를 통째로 뒤흔들어야 하는 대공사가 될 것입니다.
